# ERP 구축용 AI 코딩 프롬프트팩

이 문서는 `ERP_구축_제안요청서_RFP_v0.3.md`를 실제 구현으로 옮기기 위한 순차 실행 프롬프트다. RFP가 제품 요구사항의 원본이며, 이 문서는 구현 순서와 품질 게이트를 정의한다.

## 사용 원칙

1. STEP 0부터 순서대로 실행한다. 뒤 단계는 앞 단계의 코드·문서·시험을 전제로 한다.
2. RFP 필수(M) 요구사항만 기본 구현한다. 선택(O)은 별도 승인 후 구현한다.
3. 요구사항 제목만 보고 완료 처리하지 않는다. 각 ID에 구현 위치와 시험 증적을 연결한다.
4. 미확정 DEC가 해당 단계에 영향을 주면 임의로 결정하지 말고 질문 목록과 추천안을 제시한 뒤 멈춘다.
5. 설계·데이터 마이그레이션·범위 변경은 승인 게이트로 삼고, 승인된 범위 안의 통상 구현은 계속 진행한다.
6. 재고·회계·채권채무·결재·감사로그의 정합성은 화면 완성도보다 우선한다.
7. 각 단계에서 새로 발견한 요구사항은 임의 구현하지 않고 추적표의 `CHANGE_REQUEST`로 기록한다.

## 모든 단계에 공통으로 붙이는 완료 규칙

```text
[공통 완료 규칙]
- 시작 전 현재 코드와 docs/requirements-traceability.md를 읽고 이번 단계의 대상 ID를 선언한다.
- 구현 계획은 10줄 이내로 제시한 뒤, 미확정 DEC·파괴적 변경·범위 증가가 없으면 구현을 계속한다.
- 라우터는 인증·권한·입력검증·서비스 호출만 담당하고 비즈니스 규칙은 서비스에 둔다.
- 모든 서버 입력은 스키마로 검증하고, 화면 권한과 별개로 서버에서 권한·데이터 범위를 검사한다.
- 변경 후 format, lint, typecheck, unit test, integration test, build를 실행한다.
- UI가 포함되면 핵심 흐름 E2E와 PC·모바일 뷰포트 확인을 추가한다.
- 실패를 숨기거나 테스트를 삭제·완화하지 않는다. 실패 원인과 미완료 항목을 정확히 보고한다.
- 완료한 요구사항 ID마다 구현 파일·자동시험·수동 확인 결과를 추적표에 연결한다.
- 완료 보고에는 대상 ID, 변경 파일, DB 변경, 시험 명령과 결과, 수동 확인, 잔여 위험을 포함한다.
```

## STEP 1 — 저장소 헌장과 아키텍처

```text
승인된 RFP, 요구사항 추적표, 결정 레지스터를 기준으로 구현 헌장을 작성한다. 아직 업무 기능은 구현하지 않는다.

[기술 기준]
- Next.js App Router + TypeScript strict
- PostgreSQL + Prisma
- tRPC, zod 입력검증, API 정밀 숫자는 문자열 직렬화
- Tailwind CSS + shadcn/ui + TanStack Table
- DEC-07에서 승인된 세션 인증, 배포환경, 비공개 객체 저장소
- Vitest 또는 동등한 단위·통합시험, Playwright E2E

[작성 파일]
1. docs/engineering-rules.md — 도구 중립적인 전체 규칙
2. AGENTS.md — 저장소 작업 규칙과 docs/engineering-rules.md 필독 지시
3. CLAUDE.md — 동일한 원칙을 참조하는 도구별 진입 문서
4. docs/architecture.md — 모듈경계, 요청 흐름, 배포구조
5. docs/transaction-contract.md — 트랜잭션·멱등성·취소·아웃박스 계약
6. docs/security-model.md — 인증, RBAC, 데이터 범위, 민감정보, 파일 보안
7. docs/adr/ — 승인된 DEC와 기술결정별 ADR

[반드시 명문화할 불변조건]
- 금액·수량에 float를 사용하지 않는다. DB는 Decimal, API는 정밀 문자열, 애플리케이션은 decimal 라이브러리를 사용한다.
- 모든 업무전표는 명시적 상태머신과 version을 가진다.
- 확정 전에는 원장에 영향을 주지 않으며 확정 후 직접 수정하지 않는다.
- 재고·회계 원장행은 삭제하지 않는다. 취소는 반대원장·역분개로 처리한다.
- 서비스 쓰기 함수는 tx, actor, requestId를 받는다. 하위 서비스가 독립 트랜잭션을 열지 않는다.
- 승인·확정·취소·배분은 requestId와 DB 유일성 제약으로 멱등성을 보장한다.
- 감사로그는 업무 변경과 같은 트랜잭션에서 저장하고 민감필드를 제거한다.
- 이메일·메신저·예약작업은 트랜잭셔널 아웃박스로 커밋 후 처리한다.
- 서버의 모든 조회·쓰기·다운로드에서 RBAC와 부문·창고·인사 데이터 범위를 적용한다.

파일 길이 같은 기계적 기준보다 모듈 응집도와 시험 가능성을 우선한다. 생성 파일에는 수동 길이 제한을 적용하지 않는다.

문서 간 충돌과 아직 승인되지 않은 결정이 없는지 확인해 보고해라.
```

## STEP 5 — 전자결재 코어(APV)

```text
전자결재 필수 요구사항 APV-01~15를 구현한다. APV-16은 옵션 승인 시에만 구현한다.

[모델]

- ApprovalRule, ApprovalLineTemplate, ApprovalLineTemplateStep
- Delegation: 대결자와 유효기간
- ApprovalDocument, ApprovalStep, ApprovalParticipant
- ApprovalLink: targetType, targetId, targetVersion, 유일성 제약
- ApprovalActionLog, Attachment 연결

[상태와 처리]
- DRAFT, IN_PROGRESS, ON_HOLD, APPROVED, REJECTED, WITHDRAWN, CANCELED
- 순차결재, 병렬합의, 참조·열람, 보류·회수·수정 후 재상신
- 양식 버전과 문서 본문 스냅샷을 보관해 과거 문서를 재현
- 조직·금액·직위 규칙과 대결 유효기간으로 실제 결재단계를 생성
- 승인·반려는 문서 version으로 낙관적 동시성 검사를 수행
- 같은 요청의 중복 승인에서 단계가 두 번 진행되지 않도록 requestId와 DB 제약 사용

[연동 계약]
- ApprovalTargetHandler 인터페이스를 정의한다.
- validateBeforeSubmit, onApproved, onRejected, onCanceled는 같은 TransactionContext를 받는다.
- 프로세스 메모리 등록 여부에 의존하지 않도록 targetType별 명시적 resolver를 사용한다.
- 아직 없는 구매·전표 핸들러는 구현하지 말고 계약 테스트용 fake handler만 둔다.

[기능·화면]
- 동적 양식관리와 기본 양식 6종 시드
```


## STEP 10 — 결재·매출·재고·회계 통합

```text
- 이메일·메신저만 커밋 후 아웃박스 작업자가 처리한다.

[필수 E2E]
1. 견적→주문→매출전표→결재→확정→출고→분개→수금→채권소진

3. 휴가신청→결재→연차사용원장→근태반영
4. 확정 전표 취소→재고 반대원장→채권채무 원복→회계 역분개

[장애주입 시험]
- 재고 성공 후 회계 실패를 발생시켜 전체 롤백 확인
- 승인 요청을 동시에 두 번 보내 중복 부작용 없음 확인
- DB 커밋 후 이메일 실패 시 업무는 유지되고 아웃박스만 재시도되는지 확인

통합시험이 통과할 때만 관련 요구사항을 DONE으로 변경한다.
```

## 보조 프롬프트

### 요구사항 누락 감사

```text
RFP와 docs/requirements-traceability.md를 대조하라. DONE인 각 ID에 실제 구현 파일과 실행되는 시험이 존재하는지 확인한다. 제목만 언급했거나 시험이 비어 있거나 다른 ID의 기능을 근거로 재사용한 항목을 찾아 NOT_VERIFIED로 되돌리고 이유를 보고하라. 아직 코드는 고치지 마라.
```

### 트랜잭션 경계 감사

```text
승인·확정·취소·수금배분 서비스의 호출 그래프를 작성하라. 하위 서비스가 독립 트랜잭션을 열거나, 감사로그가 커밋 밖에서 기록되거나, 외부 이메일이 커밋 전에 호출되거나, requestId 유일성 제약이 없는 지점을 파일·라인과 함께 보고하라. 장애주입 시험으로 원자성을 검증하라.
```

### 민감정보 감사

```text
주민번호·계좌번호·비밀번호·세션·첨부 접근 URL이 DB, 감사로그, 애플리케이션 로그, 오류응답, 엑셀·PDF에 어떻게 흐르는지 추적하라. 권한·암호화·마스킹·보유기간 위반을 파일·라인과 함께 보고하고, 테스트로 재현한 뒤 수정하라.
```

### 재고·회계 대사

```text
InventoryLedger와 StockSnapshot, 업무전표와 채권채무, 업무전표와 JournalEntry를 전수 대조하는 검증 명령을 실행하라. 불일치 건수와 원천 ID를 보고하고 원인을 찾되 원장행을 직접 수정하거나 삭제하지 마라. 승인된 복구 서비스로만 재생성하라.
```

### 단계 완료 리뷰

```text
이번 단계 대상 요구사항 ID별로 구현·시험·수동검수 증거를 표로 제시하라. INT-01~12와 보안 요구사항 위반을 별도로 확인한다. 증거가 없는 항목은 DONE으로 표시하지 마라. 발견된 문제는 심각도, 영향, 재현법, 최소 수정안 순으로 보고하라.
```
